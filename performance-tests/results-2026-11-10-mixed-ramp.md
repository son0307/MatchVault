# 2026-11-10 Oracle 혼합 순위 100→250 VU 비교

## 조건

- 대상: `https://matchvault.site`, k6 `performance-tests/ranking-cache-ramp.js`
- 패턴: 100 VU 20초 → 1초 동안 250 VU로 증가 → 250 VU 10초 → 1초 동안 100 VU로 감소, 3회 반복. 단계 시간 96초.
- 조회: 리그 39, 2024·2025·2026 시즌마다 리그 선수 순위·리그 팀 순위·팀 선수 순위 4개. 준비 단계에서 고른 팀 ID 목록은 두 실행에서 동일했다.
- 각 VU가 18개 조회 키를 순환하며 요청 사이에 0.1초 대기. k6 요청 타임아웃은 10초.
- 비잠금형 배포: `594c268`, [Actions 42748127877](https://github.com/son0307/MatchVault/actions/runs/42748127877), `match-vault-green`.
- 키별 잠금형 배포: `d1ea96f`, [Actions 42749054012](https://github.com/son0307/MatchVault/actions/runs/42749054012), `match-vault-blue`.
- 두 배포 모두 워크플로 성공과 공개 헬스체크 HTTP 200을 확인했다. 현재 배포는 키별 잠금형이다.

두 모드 모두 피크 실패율 1% 미만 threshold를 넘었고, 다수의 요청이 10초 타임아웃을 기록했다. 이번 혼합 키·250 VU 실행은 **키별 잠금형의 응답 성능 개선을 보여 주지 않는다**. 전체 p95와 실패율은 잠금형이 높았고, 성공 응답만의 p95는 잠금형이 조금 낮았다. 부하 발생기에서 관측된 응답 차이만으로 원인을 잠금 구현으로 확정할 수 없다.

잠금형의 기본 대기 상한도 10초이므로 k6가 10초에 요청을 끊으면 대기 초과 후의 제한된 DB 직접 조회 응답을 관찰하기 어렵다. 18개 키는 동일 키 스탬피드뿐 아니라 서로 다른 키의 동시 집계도 유발한다. 캐시 상태·외부 트래픽·DB 부하는 두 실행에서 고정하지 않았다. 순위 캐시 값 TTL은 10분이며 실험 간에는 각 모드의 서로 다른 캐시 키 공간을 사용했다.

두 버전의 세 순위 서비스에는 `Ranking aggregation started.` 로그가 있다. 사용자가 Kibana에서 두 실험 시간 범위의 로그와 키별 건수를 확인했다. 두 모드 모두 요청 대상인 18개 조회 키가 전부 집계됐으며, 잠금형에서는 각 키가 정확히 한 번씩 집계됐다.

| 순위 종류 | 조회 키 수 | 비잠금형 집계 진입 | 키별 잠금형 집계 진입 | 비잠금형 중복 진입 |
| --- | ---: | ---: | ---: | ---: |
| 리그 팀 순위 | 3 | 17 | 3 | 14 |
| 리그 선수 순위 | 3 | 8 | 3 | 5 |
| 팀 선수 순위 | 12 | 19 | 12 | 7 |
| 합계 | 18 | 44 | 18 | 26 |

비잠금형에서 중복 진입은 리그 팀 순위에 가장 많이 발생했다. 리그 39의 2024·2025 시즌 팀 순위는 각각 6회, 2026 시즌은 5회 집계됐다. 집계 진입 횟수는 전체 44회에서 18회로 26회, 약 59.1% 줄었다. 이 수는 실제 SQL 문 실행 횟수와 다르며, 사용자 제공 Kibana 기록에 근거한다.

동일 키에서 비잠금형 10회·잠금형 1회가 관측된 기존 로컬 실험은 [2026-11-02 결과](results-2026-11-02.md)에 별도로 기록돼 있다.

원본 k6 요약은 로컬 `build/performance-tests/ramp-baseline-summary.json`과 `ramp-locking-summary.json`에 저장했다.
