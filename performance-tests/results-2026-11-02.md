# 순위 캐시 키별 잠금: 로컬 50 VU 버스트

## 이전 테스트 자료

이전 2025 시즌 테스트의 재현 조건과 스크린샷은 `docs/Redis 캐시 스탬피드 대응.md`에 있다. 당시 실행 스크립트는 저장소와 로컬 `load-tests` 디렉터리에서 찾지 못했다. 당시 잠금형 Writer 적용 후 2025 리그 선수 순위 50 VU의 p99는 250.59ms, 실패율은 0%, 최대 응답시간은 1.74초였다. 아래 결과는 다른 시점의 로컬 서버와 데이터로 측정했으므로 절대 지연을 직접 비교하지 않는다.

## 조건

- 대상: 로컬 `127.0.0.1:8080`, 앱 프로세스는 새 클래스 빌드 이후 시작함
- k6 `per-vu-iterations`: 50 VU, VU당 요청 1회
- 테스트 직전 로컬 Redis의 해당 순위 캐시 세대 번호만 올려 cold miss 유도
- 각 요청은 HTTP 200과 비어 있지 않은 순위 응답을 검증
- `ranking_request_duration`은 k6 준비 단계 요청을 제외한 순위 API 응답 시간

| 케이스 | 시즌·대상 | 성공 | p95 | p99 | 최대 |
| --- | --- | ---: | ---: | ---: | ---: |
| 동일 키 | 2025 리그 선수 순위 | 50/50 | 270.09ms | 272.48ms | 272.51ms |
| 혼합 시즌 | 2023·2024·2026 리그 선수 순위 | 50/50 | 310.31ms | 312.92ms | 314.92ms |
| 혼합 팀 | 2024·2025·2026, 시즌별 4팀 선수 순위 | 50/50 | 127.81ms | 142.29ms | 142.29ms |
| 혼합 API | 2024·2025·2026, 리그 선수·리그 팀·팀 선수 순위 | 50/50 | 263.94ms | 263.94ms | 263.94ms |

## 같은 로컬 환경의 비잠금형 기준선

서버를 로컬 전용 `ranking.cache.baseline-nonlocking=true`로 재시작해 순위 캐시도 실제 기본 `cacheManager`를 사용하게 했다. 10 VU 확인 후 Redis에 세대 번호가 없는 순위 캐시 키가 생성된 것을 확인했다. 각 버스트 직전에는 해당 캐시의 엔트리만 제거했다. 아래 네 케이스는 위 키별 잠금 테스트와 동일한 시즌·팀 분포와 50 VU를 사용했다.

| 케이스 | 키별 잠금 p99 | 비잠금형 p99 | 비잠금형 성공 |
| --- | ---: | ---: | ---: |
| 동일 키 | 272.48ms | 349.51ms | 50/50 |
| 혼합 시즌 | 312.92ms | 490.23ms | 50/50 |
| 혼합 팀 | 142.29ms | 164.43ms | 50/50 |
| 혼합 API | 263.94ms | 328.60ms | 50/50 |

이번 로컬 실행에서는 네 케이스 모두 키별 잠금 방식의 p99가 낮았다. 비잠금형도 HTTP 실패나 빈 응답은 없었다. 집계 실행 횟수와 DB 커넥션·CPU 지표를 수집하지 못했으므로, 비잠금형에서 스탬피드가 실제 몇 번 발생했는지 또는 p99 차이의 원인이 잠금 방식 하나인지까지는 단정하지 않는다. 각 방식은 한 차례씩만 측정했으며 서버 재시작 시점도 달랐다.

측정 후 비교용 인자를 제거하고 서버를 재시작했다. 정상 모드의 순위 요청이 다시 세대 번호가 포함된 Redis 캐시 키를 생성하는 것을 확인했다.

처음 시도한 2021·2022·2023 혼합 시즌 테스트에서는 HTTP 오류는 없었으나 2021·2022 시즌의 선수 순위가 빈 응답이어서 34/50건의 데이터 검증이 실패했다. 이 실행은 성능 비교에서 제외했다. 팀 순위에는 해당 시즌 팀이 20개씩 있어도 선수 집계 데이터가 있다는 뜻은 아니었다.

## 해석 범위

이 실행에서 HTTP 503과 응답 데이터 검증 실패는 없었다. 따라서 정상 부하에서의 응답 성능은 확인했지만, **10초 대기 초과와 Redis 장애 시 DB 직접 조회 제한**은 이번 부하로 발생시키지 못했다. 앱의 `ranking.cache.load`·`ranking.cache.wait` 메트릭을 읽을 수 있는 관리 엔드포인트가 로컬에서 404를 반환해 집계 실행 횟수와 잠금 대기 분포도 확인하지 못했다. 키별 병렬 계산이 실제로 몇 건 일어났는지는 서버 메트릭을 수집한 뒤 별도로 검증해야 한다.

원본 k6 요약과 시계열 JSON은 로컬 `build/performance-tests/`에 저장했다. 실행 방법은 `performance-tests/README.md`를 참고한다.
